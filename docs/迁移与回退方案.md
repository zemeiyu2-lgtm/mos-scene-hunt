# 迁移与回退方案（V1）

本文件是**上线操作的依据**：先切注册表、再导入历史作品、验证后再下线旧路径；任何一步失败都能回到上一步。

---

## 1. 变更面

| 变更 | 是否影响已发布内容 | 可回退性 |
|---|---|---|
| 新增 registry（`works/`、`users/`、`sessions/`、`audit/`） | 否 | 删除目录即回到零 |
| `POST /api/publish` 改为「登录 + 归属 + 进审核」 | 是（写入路径） | 代码回退，历史对象未被改写 |
| `GET /api/games/{id}` 改为查注册表 | 是（读取路径） | 代码回退即恢复旧行为 |
| 历史作品导入 | 否（只读旧对象，写新文档） | 删除对应 work 文档即撤销 |

**没有任何一步删除或重写历史游戏对象。** 这是整个方案能回退的前提。

---

## 2. 上线顺序（正式环境）

### 步骤 0：环境准备（需授权）

```bash
REGISTRY_STORE=blob                 # 必须；文件存储在 serverless 会丢数据
BLOB_READ_WRITE_TOKEN=***           # 只读旧对象 + 读写 registry 都靠它
BOOTSTRAP_ADMIN_EMAIL=...           # 一次性；首次访问 /admin/login 时创建
BOOTSTRAP_ADMIN_PASSWORD=...        # 一次性；登录后立即改密并删除该变量
PUBLISHED_GAMES_STORE=blob          # 旧对象与 registry 使用同一 Blob 存储
```

未配置 `BLOB_READ_WRITE_TOKEN` 时，`/api/admin/import-legacy` 会明确返回
「列表不完整」而不是假装成功。

### 步骤 1：部署代码，但先不导入

此时 registry 为空 → 所有 `GET /api/games/{id}` 返回 404。
**这是预期行为**：宁可短时间不可读，也不要在归属未确认时让内容继续可读。

若不能接受这段窗口，改用步骤 1':先部署代码，再立即执行步骤 2，全程在一个部署窗口内完成。

### 步骤 2：演练（不写任何数据）

```bash
BASE_URL=https://正式域名 \
ADMIN_EMAIL=... ADMIN_PASSWORD=... \
node scripts/import-legacy.mjs
```

输出每个作品的判定：`上线` / `隔离` / `跳过(已存在)` / `跳过(id非法)`。
判定规则：

| 判定 | 条件 | 结果状态 |
|---|---|---|
| 上线 | `meta.latestVersionId` 存在、包校验通过、字节哈希等于文件名 | `published`，公开可读 |
| 隔离 | meta 缺失/不可解析、最新版本缺失/校验失败/哈希不符 | `draft`，**不公开**，版本记录保留 |
| 跳过(已存在) | registry 已有同 `gameId` | 不做任何修改 |

**演练结果必须人工过一遍**，特别是「隔离」列表：它意味着该作品的历史链接在切换后不可读。

### 步骤 3：执行导入

```bash
... node scripts/import-legacy.mjs --apply
```

- 只写 registry，**不 put / 不 delete / 不覆盖**任何游戏对象；
- 每个作品一条审计 `work.import_legacy`；
- 重复执行安全（第二次全是「跳过(已存在)」，`revision` 不变）。

### 步骤 4：逐项核对

```bash
# 抽查：任取 3 个历史作品，比较切换前后的字节
curl -s https://正式域名/api/games/<id> | sha256sum
```

再打开每条历史分享链接确认可玩；隔离项由管理员在后台补审后发布。

### 步骤 5：归属认领

导入后的作品归属 `legacy-import@mos-scene-hunt.invalid`（该账号 `status=suspended`，**无法登录**）。
管理员在后台作品详情页「转移作品归属」逐个指派给真实作者。转移不改变状态与线上版本。

## 3. 回退

### 3.1 回退代码（最常见）

```bash
git revert <上线提交>
```

因为旧对象从未被改写，回退后旧读取路径立即恢复，历史链接自动可用。
registry 目录可保留（无害），也可清空。

### 3.2 回退单个导入

后台把该作品归档（`archive`）→ 公开读取 404，历史仍在。
需要彻底移除时删除 `works/<gameId>.json`（Blob 对象路径同名），不影响游戏对象。

### 3.3 回退整个导入

删除 `legacy-import@mos-scene-hunt.invalid` 名下的全部 work 文档。
**不要**删除 `published-games/` 下的任何对象——它们是历史真相。

### 3.4 数据模型版本

`schemaVersion: 1`（`WorkRecord.schemaVersion`）。读取方对未知版本应拒绝而非猜测：
当前 `REGISTRY_SCHEMA_VERSION = 1`，升级时按「旧文档可读、新字段可选」的原则演进，
不引入需要重写全部文档的破坏性变更。

## 4. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 导入判定为「隔离」的历史作品链接失效 | 玩家打开 404 | 演练阶段先列出清单，人工确认后再 apply |
| Blob 无 CAS，并发写丢更新 | 一次审核决定可能丢失 | 单实例锁 + `revision` 409；版本对象内容寻址不受影响 |
| `BLOB_READ_WRITE_TOKEN` 缺失 | 无法列举/读写 | 明确报错并停止，不降级到本地文件假装成功 |
| 一次性管理员口令泄露 | 后台被接管 | 登录后立即改密、删除 `BOOTSTRAP_ADMIN_*` 变量；引导仅在「无 admin」时生效，二次调用返回 `admin_exists` |
| 文件存储用于正式环境 | 重启丢数据 | 正式环境强制 `REGISTRY_STORE=blob`，Preview 的 `/tmp` 仅用于验收 |
