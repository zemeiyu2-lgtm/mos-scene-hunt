# MOS Scene Hunt｜游戏包标准 V1.0

## 1. 标准定位

MOS Game Package 是 MOS Scene Hunt 在设计端、云端、游玩端之间交换游戏内容的统一标准。

标准协议名称：`mos-scene-hunt-game`
标准协议版本：`1.0`

正式 JSON 包：
```json
{
  "format": "mos-scene-hunt-game",
  "formatVersion": "1.0",
  "game": { "...": "Game 内容" },
  "assets": []
}
```

## 2. 最重要的版本分离

`formatVersion` 是游戏包协议版本；`game.version` 是具体游戏的内容版本。

例如：
`formatVersion = 1.0`
`game.version = 2.3.0`

协议升级不应强制修改游戏内容版本。

## 3. Game 核心模型

V1.0 沿用当前 Game 模型：
`id / language / title / description / author / version / estimatedMinutes / difficulty / startLocation / huntArea / entrySceneId / scenes / aiProfile`

`id` 是稳定身份；改名不改变 id。
`version` 是内容版本。

## 4. Scene

每个体验点至少具有：
`id / title / story / location / nextSceneId`

可选：
`briefing / challenge / reward / media / hint / npc / dialogue / ar / place / mapStyle`

GPS 使用 WGS84。`location.radius` 是实际触发半径。
最终场景使用 `nextSceneId = null`。

## 5. Challenge

V1.0 支持：`text / choice / keyword`。
`reflective = true` 表示反思式选择，不进行对错评分。
AI 不得绕过确定性游戏引擎直接改变 GPS、解锁或奖励逻辑。

## 6. Reward

支持：`keyword / item / badge / story`。

## 7. Media 与 Assets

当前场景媒体可引用本地数据 URL 或 HTTP/HTTPS URL。
包级 `assets` 为未来云端资源存储预留。
V1.0 暂不强制 ZIP，也不要求所有资源嵌入包内。

## 8. 导入兼容

V1.0 正式包使用包封装。
同时继续接受旧版直接以 Game 对象作为根对象的 JSON。
Legacy 可以导入；新的 JSON 导出统一使用 V1.0 包封装。

这样现有 BSOP、IGSL 等游戏无需一次性重做。

## 9. Word / Markdown 的定位

Word 和 Markdown 是设计输入/编辑格式，不是云端游戏标准。

统一流程：
Word / Markdown / JSON / 设计器 / AI
→ Game
→ MOS Game Package V1.0
→ 云端发布或本机游玩

## 10. 云端边界

云端保存游戏身份、版本、游戏包、作者、发布状态、审核信息和资源。
云端不修改游戏运行逻辑。

发布后的基本流程：
云端 → 下载 V1.0 游戏包 → 本机验证 → 本机保存 → 离线游玩。

## 11. 验证

导入依次进行：包结构、Game 结构、场景引用、GPS、空间、游戏逻辑、媒体基础检查。

存在 error：不允许进入可试玩状态。
只有 warning：允许继续，但必须显示提醒。

## 12. V1.0 暂不纳入

用户账号、团队权限、审核记录、下载统计、支付、在线聊天、实时多人状态、云端游戏进度、强制联网、QR Code、强制 ZIP 封装。

这些属于平台层，不属于游戏包核心。

## 13. 未来兼容

小版本尽量向后兼容；大版本允许结构性变化。
游玩端必须识别不支持的 formatVersion 并明确提示，不能静默解释未知版本。

## 14. V1.0 冻结闭环

必须验证：

Word → Game → V1.0 JSON → 导入 → 验证 → 本机游戏库 → 手机试玩。

以及：

V1.0 JSON → 云端目录 → 下载 → 本机游戏库 → 手机试玩。

以及：

V1.0 JSON → Markdown → 再导入 → Game。

最终原则：

> 同一个游戏在不同入口之间移动时，不能丢失可游玩的核心信息。
