# 后台管理平台：架构与数据模型（V1）

本文说明 `feat/admin-platform` 分支交付的后台平台**实际实现**，与设计文档
`MOS-Scene-Hunt-后台总体设计与分阶段实施方案-V1.0.md` 的对应关系见每节末尾。

---

## 1. 一句话架构

公开读取与写入不再直接面向「文件路径」，而是面向**注册表（registry）**：作品有归属、版本有审核状态、
只有被显式发布的版本才对外可读。历史对象（`published-games/<gameId>/...`）原样保留，通过一次性导入
把「归属 + 状态」补登记进来，不重写字节。

```
                    ┌──────────────────────────────┐
  创作者 POST /api/publish ──► 身份校验 ──► 归属校验 ──► 写不可变版本对象
                    │                                   │
                    │                                   ▼
                    │                          registry: Works/Submissions
                    │                                   │
  审核者 POST /api/admin/works/{id}/claim|decision ──────┤
                    │                                   │
  管理员 POST /api/admin/works/{id}/publish|withdraw ───┘
                    │
                    ▼
  GET /api/games/{id}  ──► registry 查 publishedVersionId ──► 读版本对象
                          非 published/unlisted → 404（与「不存在」同体）
```

关键点：**公开读取只看 `publishedVersionId`**，永不看 `latestVersionId`。
「最新提交」与「当前上线」是两个不同事实，混用会让未审内容直接上线。

对应设计文档：§3 架构、§4 数据模型、§5 状态机。

## 2. 三条硬约束（实现层面如何落地）

| 约束 | 落地位置 | 违反会怎样 |
|---|---|---|
| 审核元数据绝不进游戏包，`formatVersion` 恒为 `1.0` | `lib/registry/types.ts` 顶部注释 + `WorkRecord` 独立存储 | 老客户端/离线包会解析失败，已发布内容不可回滚 |
| `gameId` 一旦入库即锁定归属 | `service.submitVersion`：`canClaimGameId()` → 已存在且非本人 → 403 `game_id_taken` | 任何人可用他人 id 覆盖其默认链接（**P0**） |
| 公开读只认 `publishedVersionId` | `app/api/games/[gameId]/route.ts` | 未审内容可读（**P0**） |

## 3. 数据模型

### 3.1 实体

| 实体 | 键 | 说明 |
|---|---|---|
| `UserRecord` | `users/<id>.json` | scrypt 口令散列 + 盐；角色 `creator < reviewer < admin`；`status` 为 `active/suspended` |
| `SessionRecord` | `sessions/<tokenHash>.json` | 库内**只存** `sha256(token)`；含 `expiresAt`、`revokedAt`、IP/UA 截断散列 |
| `WorkRecord` | `works/<gameId>.json` | **聚合根**：作品 + 全部版本 + 全部提交记录，一次写入即一个原子状态变更 |
| `AuditRecord` | `audit/<时间序>.json` | 谁在何时对什么做了什么（含 before/after 摘要） |

`WorkRecord` 采用「一作品一文档」而非关系表，原因写在 `types.ts` 注释里：Blob 适配器**没有
compare-and-swap**，多对象事务无法保证原子；单文档写入是唯一能保证「状态变更要么全成要么全不成」的形态。
队列/统计因此是**扫描**而非查询，这是明确记录在案的扩展边界（见 §6）。

### 3.2 作品状态机（10 态）

```
draft ──submit──► submitted ──claim_review──► in_review ──decide(approve)──► approved ──publish──► published
  ▲                  │                          │                                                  │
  │                  │                          └──decide(reject)──► rejected                    unlist ◄─► published
  └──changes_requested ◄──decide(request_changes)                                                  │
                                                                                              withdraw ──► withdrawn
任意态 ──archive──► archived ──restore──► (该作品曾上线则 published，否则 approved)
```

公开可读集合 = `published ∪ unlisted`（`isPubliclyReadable()` 是唯一判据，读取接口直接复用）。

### 3.3 关键语义修正（实现期发现并修正）

设计初稿把审核动作绑定在**作品主干状态**上，实现时发现两个真实缺陷：

1. **已上线作品提交新版本会把 `state` 改回 `submitted`** → 旧公开链接立即 404。
   修正：`submit` 只在作品**当前不可公开读**时才改主干状态；审核动作绑定 **submission** 记录。
2. **审核队列按作品状态筛选会漏掉「已上线作品的待审更新」** → 更新永远排在队尾看不见。
   修正：`reviewQueue()` 按 submission 状态（`pending`/`in_review`）排队。

两处都有回归测试：`tests/registry/state-machine.test.ts`、`tests/e2e-admin/run.mjs`
（"新版本待审期间，公开读取仍是首版"）。

## 4. 持久层：双适配器

| 适配器 | 选择方式 | 写入语义 | 适用 |
|---|---|---|---|
| 文件 | 默认（`REGISTRY_DIR`） | 写临时文件 → `rename` → **读回校验**；进程内 per-key 锁；`revision` 乐观并发 | 本地开发、单机部署 |
| Vercel Blob | `REGISTRY_STORE=blob` | `allowOverwrite` 用于可变文档；`list()` **显式分页**（`hasMore`/`cursor`） | 多实例 / 需要跨重启持久 |

**如实说明的限制**：Blob 无 CAS，两个实例同时写同一作品时可能后写覆盖先写。缓解手段：
① 版本对象内容寻址、先写后登记，永远不会被覆盖；② `revision` 冲突返回 409 要求刷新；
③ 单实例内 per-key 锁串行化。**没有**假装这个问题不存在——它写在 `lib/registry/store.ts` 与状态卡上。

## 5. 请求路径与鉴权顺序

以「发布」为例（`app/api/admin/works/[gameId]/[action]/route.ts`）：

```
1. isValidGameId()          → 400（在读任何文档之前，不泄露存在性）
2. requireRole(admin)       → 401/403（角色检查先于作品读取）
3. assertSafeMutation()     → 415/403（application/json + Origin 同源）
4. 读取作品 + 纯函数状态迁移 → 409（非法迁移）
5. putWork(revision)        → 409（并发冲突，重试一次）
6. appendAudit()            → 失败只记日志，不回滚（作品文档才是权威）
```

顺序本身是安全属性：**角色检查早于数据读取**，所以 403 不可能被用来探测某个 gameId 是否存在。

## 6. 已知边界（不隐藏）

| 边界 | 影响 | 现状 |
|---|---|---|
| 队列 = 全表扫描 | 作品数到数千后列表变慢 | 记录在案；需要索引时再加二级索引对象 |
| 限流为单实例内存 | 多实例部署下限流被放大 N 倍 | 登录失败计数已持久化（真正防爆破的那层）；接口限流为第二层 |
| Blob 无 CAS | 极端并发下可能丢一次元数据更新 | 版本对象永不丢失；冲突返回 409 |
| Preview 用文件存储 | 容器重启后数据消失 | Preview 仅用于验收；正式环境必须 `REGISTRY_STORE=blob` |

对应设计文档：§2 能力盘点、§9 存储与访问控制矩阵、§12 阶段划分。
