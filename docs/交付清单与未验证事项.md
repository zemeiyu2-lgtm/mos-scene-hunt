在 Preview 上**实际验证到**的行为（不是本机推测）：

1. 生产级 Cookie 名称 `__Host-mos_sess` 在 HTTPS 下正常签发与回读——本机单测覆盖不到的那一层；
2. 匿名提交 401、匿名调后台接口 401；
3. 创作者提交 201 → 未审内容公开读 404（含 `?v=`）→ 审核通过仍 404 → 发布后 200；
4. 管理员用他人 `gameId` 提交被 403 `game_id_taken`；
5. 新版本待审期间线上仍是旧版；发布后切新版，旧 `?v=` 仍返回原字节且标注 `immutable`；
6. 撤下 → 404；恢复 → 内容与撤下前一致；
7. 后台页面（首页/队列/作品详情/审计）对已登录管理员 200，匿名访问重定向登录；
8. 登出后会话立即失效（401）；
9. 数据在**独立进程、独立连接**下仍可读（跨进程持久性实测）。

**Preview 的限制（必须知道）**：文件存储在容器重启/重新部署后清空，仅用于验收。

### 2.3 历史导入 apply 实测（关键：历史不被改写）

用旧布局（`<gameId>/meta.json` + `<gameId>/versions/<vId>.json`）构造一份历史作品，
在**同一台服务器**上完整走一遍：

```
导入前 GET /api/games/legacy-hunt-mvsb30si      → 404（registry 里没有）
node scripts/import-legacy.mjs                  → DRY RUN：可上线 1 / 已存在 3，未写任何数据
node scripts/import-legacy.mjs --apply          → 写入 registry
导入后 GET /api/games/legacy-hunt-mvsb30si      → 200，返回原游戏包
sha256sum -c（导入前后的对象哈希）               → 两份对象均 OK，字节未变
```

导入后的作品文档：`state=published`、`publishedVersionId=dc8648f1dccbe934`、
版本状态 `approved`、归属 `legacy-import@mos-scene-hunt.invalid`（`role=creator`、
`status=suspended`，无可用口令，**无法登录**）。审计留有 2 条 `work.import_legacy`
（逐作品 + 批次汇总）。

结论：**历史作品可以被接回读取路径，而字节一个也没动。** 这是「保护历史作品」这条要求的直接证据。

## 3. 本机运行方式

```bash
npm install
REGISTRY_STORE=file REGISTRY_DIR=./.registry \
BOOTSTRAP_ADMIN_EMAIL=admin@local.test BOOTSTRAP_ADMIN_PASSWORD='<自定>' \
npm run dev            # http://127.0.0.1:3000/admin/login
```

- 首次打开 `/admin/login` 触发一次性管理员引导（仅当库里没有 admin）；
- 登录后到 `/admin/users` 改密、建创作者账号；
- 测试：`npx vitest run`；端到端：`node tests/e2e-admin/run.mjs http://127.0.0.1:3000`。

| 事项 | 原因 |
|---|---|
| `ce03ff5` 在 Preview 上的表现 | 重部署时发布服务 DNS 失败；已用本机生产构建 49/49 覆盖，但**不等于** Preview 已验证 |

### 5.3 已知限制（已写进代码注释与文档）

- 限流为单实例内存，多实例会被放大 N 倍；真正的爆破防线是持久化失败计数 + 锁定；
- Blob 无 CAS，极端并发下可能丢一次元数据更新（版本对象内容寻址，永不丢失）；
- 队列为全表扫描，作品数上千后需加二级索引；
- 无自助认领：历史作品只能由管理员「转移归属」指派。
